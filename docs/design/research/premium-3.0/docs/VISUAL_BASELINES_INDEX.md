## 3. Формат збереження: чому в git ліг JPG, а PNG лишився на диску

| | PNG (оригінал зйомки) | JPG (закомічений) |
|---|---|---|
| Файлів | 32 | 32 |
| Сумарна вага | 25.3 MiB | 7.6 MiB |
| Де | `evidence/baselines/` — локально, до commit не потрапляє | `evidence/baselines-jpg/` — у commit |
| Чому не в git | `evidence/baselines/.gitignore` з `*.png` | — |

Причина проста й вимірна: `.git` цього репо важить 28 MiB, увесь `docs/` —
5.1 MiB, а 16 канонічних зображень-дошок, які є джерелом істини, лежать у
вигляді JPG по ~300 KiB. Закомітити 25 MiB PNG означало б подвоїти історію
об'єктів репо заради кадрів, які можна отримати повторно тим самим харнесом
проти того самого закріпленого білда. Конвертація — `sips -s format jpeg
-formatOptions 82`, текст і межі компонентів на ній читаються без втрати
оцінки (обидва кадри `iphone15-light-login-form` переглянуто поруч, PNG і
JPG, на дисплеї 3×).

**Наслідок, який треба пам'ятати в A4.** JPG — втратний, тому піксельні
дифи «до/після» рахуються **PNG ↔ PNG локально**, а не проти закоміченого
JPG. Для цього `manifest.json` тримає SHA-256 оригінального PNG у полі `sha256`
(він стосується файлу в `baselines/`), а рядок таблиці вище — digest JPG.
Повторити конвертацію:

```bash
cd docs/design/research/premium-3.0/evidence
for f in baselines/*.png; do
  sips -s format jpeg -s formatOptions 82 "$f" \
    --out "baselines-jpg/$(basename "${f%.png}").jpg" >/dev/null
done
```

## 4. Чого серед цих 32 кадрів немає продукту

8 файлів `*-proxy-interstitial.png` — це **не MARSHGO**. Це сторінка-попередження
сервісу zrok, через яку тепер проходить кожен перший візит на публічний URL
(кнопка «Visit Share», після неї ставиться cookie `zrok_interstitial`). Вони
зафіксовані свідомо: без проходження цієї сторінки харнес отримував не
застосунок, а заглушку, і будь-який «базис» був би фальшивим.
`dataMode = NOT_PRODUCT_infrastructure` стоїть у цих рядках саме тому, щоб
ніхто не прийняв їх за екран продукту.

Окремо: сама сторінка zrok не адаптивна — на 390 px червоний рядок з адресою
ріжеться по правому краю (видно на `iphone15-*-proxy-interstitial`). Це
інфраструктура чужого сервісу, не дефект дизайну MARSHGO, і в аудит вона не
йде.

### 7.4 Лендінг: 34.4 px → 52 px стрибком, без проміжної ступені

На телефоні заголовок бере розмір із утиліти
`text-[2.15rem]` ([ProductionMarketplace.tsx:1466](../../../../../src/views/ProductionMarketplace.tsx#L1466))

в §6.2). `clamp(52px, 6.4vw, 88px)` з `index.css:714` лежить усередині
`@media (min-width: 1024px)` (`index.css:669`), тож до десктопа він не
ділиться. Наслідок: на 1023 px заголовок — 34.4 px, на 1024 px — одразу 52 px.
Стрибок у 1.5× на одному пікселі ширини, без жодного проміжного ступеня.

Друга половина того ж рядка `:1466`: текст заголовка розбитий вручну —
`Усі способи<br/>доїхати — в одному<br/>застосунку.`. Три жорсткі переносу
працюють як макет і на 34.4 px, і на 88 px, тому на десктопі (див. кадр
`desktop-light-landing-intro`) четвертий рядок усе одно з'являється сам:
88-піксельний текст не вміщується у відведену колонку. Перенос, який мав бути
типографічним рішенням, став частиною контенту.

### 7.5 Онбординг: 25.6 px заголовка без clamp і 200 px мертвого простору

Заголовок онбордингу — 25.6 px в **усіх** в'юпортах, включно з desktop
(1440 px): те саме число в 8 записах `live-measures.json`. Той самий блок на
тому ж екрані в лендінговій гілці має clamp до 88 px. Тобто в межах одного
екрана (`auth-screen`) існують дві незалежні шкали заголовків, і онбординг
не бере участі в жодній адаптивній.

Окремо — вертикальний розподіл. Виміряно по пікселях кадру
`iphone15-light-onboarding-step.png` (1170×2532 пристрійних, тобто 390×844 CSS
при DPR 3; за фон взято нижній рядок кадру, `rgb(237, 244, 255)`):

| | CSS px | Частка висоти |
|---|---|---|
| перший рядок з вмістом | 16 | 1.9 % |
| останній рядок з вмістом | 644 | 76.3 % |
| порожньо під контентом | **200** | **23.7 %** |

Екран не прижимається ні до низу, ні до центру — вміст обривається на трьох
чвертях і далі йде суцільна смуга фону. Для порівняння, у лендінговій гілці
той самий контейнер заповнює кадри від 0 до 2531 пристрійного пікселя (фото
героя доходить до самого низу), тож механізм заповнення висоти існує — він
просто не застосований до онбордингу.

### 7.6 Desktop-лендінг: колонка CTA без прив'язки до тексту

На 1440×900 заголовок і опис стоять у лівій колонці, а дві кнопки — у правій,
над фото, візуально не пов'язані з жодною фразою, до якої відносяться
`Почати` / `У мене вже є акаунт`. Висота обох кнопок на desktop — 58 px, на
телефоні друга — 54 px; тобто навіть пара «однакова за змістом» не однакова за
мірою. Це не дефект доступності, а дефект композиції, і він зникає разом із
десктопною сіткою — тому він тут, а не в P0.

## 9. Що ці кадри змінюють у плані A1/A2

1. **Базис «до» наразі покриває лише вхід.** Порівнювати «до/після» для
   дев'яти канонічних екранів поки що нема з чим — і будь-яка оцінка «ми
   покращили Home» без такого базису буде твердженням без доказу. Перша
   вимога до власника: тестовий акаунт на прев'ю-стеку (або дозвіл його
   створити). Без цього A4 не закривається.
2. **Пріоритет боргу звужується до авторизованої частини.** До входу всі зони
   touch ≥44 px і шрифти ≥16 px (§6.2), тож D-01…D-05 — це не «уся UI», а
   конкретний набір екранів після входу. План A3 від цього тільки виграє:
   менше поверхонь, ті самі докази.
3. **Тема — не косметика, а зламаний шар.** Лендінг без теми (D-30) і
   глобальна перебивка інпутів (D-28) — це два режими, які треба лагодити до
   будь-якої нової візуальної мови: інакше третя концепція ляже на ту саму
   крихку основу.
4. **Гостьова маршрутизація потребує дизайну, а не лише редиректу.** D-29
   означає, що в A1 потрібні макети стану «гість за глибоким посиланням» —
   зараз такого екрана в застосунку фізично немає.
5. **Формат доказу узгоджений.** JPG у git, PNG локально, digestи в маніфесті,
   дифи рахуються скриптом. A4 продовжує це правило, щоб «після» було з чим
   порівняти на тих самих умовах.
